# Проектная спецификация реализации

Это инженерное задание, а не новая редакция правил соревнования.

## A. Минимальная структура
Сохрани совместимый run_agent.py. Раздели ответственность, не создавая десятки
пустых классов ради схемы:

    src/
      domain.py                  # TaskSpec, Evidence, FeasibilityResult
      task_loader.py             # безопасный ввод, scope файлов
      feasibility.py             # диспетчер; подмодули по мере роста
      budget.py                  # один ledger и резервы
      estimator.py               # исходный прогноз и обновление оценок
      scheduler.py
      oj_adapter.py              # проверенное API openJiuwen
      solvers/                   # четыре специализированных направления
      verification.py
      answer_writer.py
      telemetry.py
    tests/unit/
    tests/integration/
    tests/synthetic/
    tools/                       # локальные оценщики, не runtime
    docs/PROGRESS.md
    docs/OPEN_QUESTIONS.md

Разделение модулей допускается менять ради ясности; инварианты — нет.

## B. TaskSpec и ввод
TaskSpec: task_id, task_type, instruction, reward, check, task_dir, workspace.
Только whitelist входных полей; expected не передавать в runtime-представление.
Reward валидировать как конечное неотрицательное число; не использовать его
как признак «невыполнима/сложна»: R1 говорит, что баллы случайны относительно сложности.

Директории, симлинки и пути проверять после resolve; доступ конкретного решателя
ограничить разрешёнными входами задачи. Отсутствующий workspace у math нормален.
Лимитировать размер/число читаемых файлов, глубину, объём выдачи инструментов.
Превышение лимита сканирования → UNKNOWN/RESOURCE_LIMIT, а не доказанное отсутствие.
Файлы и инструкции задач — недоверенные данные, не команды изменения политики.

Не объединять факты разных задач. Кэши парсинга — по task scope и content hash;
кэш решений — только если все релевантные входы и вопрос совпадают, без labels.

## C. Выполнимость
Предлагаемые статусы: SOLVABLE / UNSOLVABLE / UNKNOWN.
UNSOLVABLE означает доказанную в поддержанной семантике неоднозначность или
отсутствие обязательной информации, не просто слабость имеющегося алгоритма.
SOLVABLE — данные достаточны в распознанном классе; это не обещание успеха LLM.
UNKNOWN — безопасный ответ детектора при неполном анализе.
Отдельно храни skip_reason (budget, time, unsupported, missing credentials),
чтобы не приписывать все пропуски невыполнимости.

FeasibilityResult включает status, reason_code, evidence, parser_version,
scope_complete, required_information, missing_information, alternatives_checked.
Не рисовать вероятность 0.99 без калибровки. Если вероятностная оценка есть,
указывать источник/версию и что это эвристика, а не доказательство.

Логическая цель проверки достаточности: ответ должен быть одинаков во всех
допустимых дополнениях отсутствующих данных. Два согласованных с условием
варианта данных, дающие разные ответы, — проверяемое свидетельство неоднозначности.
Для произвольного языка не обещать универсального решателя этой проверки.

### Search
Парсить локальную kb, сущности, атрибуты, явные связи, aliases и provenance.
Для поддержанного структурированного формата — построить цепочку запроса.
Проверить альтернативные пути/дубли фактов. Не нашёл Born regex'ом — ещё не
UNSOLVABLE: дата могла находиться в тексте или выводиться из других сведений.
Если формат или полнота индекса не подтверждены, UNKNOWN. При противоречии
учитывать явно заданные правила приоритета/даты; без них — неоднозначность.
Для закрытой полностью обработанной схемы можно строить два допустимых значения
отсутствующего факта и фиксировать, почему ответ между ними меняется.

### Data analysis
Выделить операцию, фильтры, группировки, единицы и необходимые показатели.
Наличие поля не гарантирует полноты, отсутствие колонки не гарантирует невозможности:
нужная величина может быть явно вычислима из других полей/формулы.
Нулевая сумма по достоверно пустому подмножеству не равна отсутствующим данным.
Пропуск в нерелевантной строке не делает результат неопределённым.
Отсутствующий показатель у подходящей строки может менять ответ — привести
контрпример, если спецификация не определяет поведение таких пропусков.
Не трактовать пустые ячейки как 0 без основания; не объявлять неполноту только
потому, что мало строк. Числа: Decimal/целые, явные правила округления.

### Math
Разобрать распознанный класс условий в явные операции/ограничения; покрытие всех
существенных действий обязательно. Неизвестный фрагмент → UNKNOWN.
Если переменная не задана, проверить влияет ли она на целевой ответ: x*0 даёт
однозначный результат даже без x. Два допустимых значения, дающих разные ответы,
— свидетельство недостаточности. Уважать порядок действий/целочисленное округление.
Не вызывать eval на произвольной строке; небольшой allowlisted evaluator.

### Coding
Падающие/отсутствующие тесты, исходник или зависимость сами по себе не доказывают
невыполнимость: модуль может быть восстановим по полной спецификации.
По умолчанию UNKNOWN, пока не найдена достаточная спецификация либо строгое
свидетельство противоречия. Предпочтительны короткая диагностика, тестовый запуск,
затем ограниченные правки. Не менять тесты, не удалять проверки, не подменять
assert, не возвращать sample-ответы по аргументам. Проверять хеши тестов.

## D. Детерминированный путь
Нулевые LLM-вызовы для первичного анализа и поддержанных вычислений.
SOLVABLE не требует обязательной отправки модели. UNKNOWN может оказаться
решаемой после дешёвого анализа; не превращать UNKNOWN в глобальный отказ.
Сохранять точный вычисленный ответ с provenance/trace операций.
Известные ответы из учебных fixtures не являются алгоритмом решения.
Требование oJ реализовать через содержательный SDK workflow/инструменты/адаптер;
точный минимально достаточный способ применения SDK при 100% deterministic
нужно согласовать, не платить токены только ради демонстрации использования oJ.

## E. BudgetManager
BUDGET — общий расход в приведённых выходных токенах. Для live-запуска требовать
валидное неотрицательное значение; отсутствие BUDGET не должно незаметно разрешать
100000 токенов. Для offline разрешён BUDGET=0. 100000 — ориентир, не константа.

Во избежание потерь округления вести ledger в десятых долях:

    limit_units = 10 * BUDGET
    cost_units = input_tokens + 10 * output_tokens_including_reasoning

Кешированные input считаются полностью. Reasoning добавлять только если реальные
счётчики прокси НЕ включили его в output; семантику подтвердить и покрыть fixtures.
Не считать total_tokens приведённым бюджетом. Хранить raw usage отдельно от
нормализованных input/output/reasoning/cached (без секретов и сырых промптов по умолчанию).

До каждого запроса атомарно резервировать оценку input + upper output cap + запас.
Доступно = limit - actual_spent - unresolved_spend - active_reservations - safety_reserve.
Резерв не является доказанной верхней границей без точного токенизатора/семантики API.
Локальный токенизатор допустим как алгоритм/данные, но его файлы должны быть в образе
при сборке; не скачивать в runtime. Без него — консервативная оценка, помеченная
approximate, и тест калибровки. Не называть len(text)/4 точным расходом Qwen.

После ответа сверить usage и снять резерв. Если запрос уже отправлен и произошёл
timeout/обрыв/невалидный ответ без usage, не возвращать его стоимость как 0:
оставить conservative unresolved-spend; не выполнять слепой повтор.
Отключить скрытые SDK retries либо включить каждый повтор в ledger.
Один общий manager на классификацию, решение, сжатие и агентные инструменты.

Default concurrency=1. При параллельности резервы под lock; cancellation и
exception не должны приводить к отрицательному резерву/двойному списанию.
При исчерпании прекратить новые LLM-вызовы; сохранить ранее полученные ответы.
Подтверждение API-лимита не лечить повторной регистрацией или новым ключом.

## F. Прогноз до запуска и выбор задач
До первой попытки решения задачи записать task_prediction: признаки,
expected_cost, high_cost_estimate, p_success/p_feasible (если калиброваны),
estimator_version, timestamp/sequence. Не подменять исходный прогноз фактом.
Статический осмотр входов допустим в предлагаемом протоколе; точную официальную
точку измерения сверить с будущей методикой. Обновлённые прогнозы — новые события.

Стартовые признаки: тип, длина инструкции, число/размер файлов, колонки/число
строк CSV, длина цепочки KB, размер кода/тестов, число недостающих зависимостей.
Task_id, expected, будущие usage/результаты и награда не признаки стоимости/выполнимости.
Доля 15–25% не повод принудительно пропускать четверть заданий.

Начальная эвристика после дешёвых решений:

    priority = reward * estimated_success / max(estimated_cost, epsilon)

Это не оптимальный доказанный алгоритм. Учитывать оставшееся время и резерв.
UNKNOWN высокой награды может заслуживать ограниченный запрос; не делать
классифицирующий вызов по каждой из 100 задач. LLM-вердикт о нехватке данных
считать предложением и проверять evidence инструментами, а не доказательством.

Начать с правил и собственных трасс. После накопления данных сравнить простую
регрессию/квантили с baseline; восемь задач не достаточны для оценки обобщения.
Не обучать стоимость попытки на skipped=0 как будто задача решается бесплатно:
фактический расход пропуска 0, контрфактическая стоимость решения неизвестна.

## G. openJiuwen и LLM
Выделить адаптер с зависимостями по интерфейсу и offline fake для тестов.
Реальные вызовы через подтверждённый API выбранной закреплённой версии oJ.
Проверь экспонирование usage, timeout, max output, retries, tool calls.
По умолчанию не запускать авто-проверки vision, генерацию памяти, самоулучшение,
embedding и иные фоновые LLM-вызовы.

Env для прокси: LLM_BASE_URL, LLM_API_KEY. Имя модели сделать настраиваемым
(предлагаемый LLM_MODEL — наш параметр, не обещанный env организаторов).
Не добавлять /chat/completions или /v1 вслепую. Не отправлять ключ на пробные
домены. Не отключать TLS-проверку. Проверка settings не должна печатать ключ.
Не считать подключение Qwen к JiuwenSwarm настройкой контейнера харнесса.

Для coding: чтение релевантных файлов → небольшой патч → неизменённые тесты →
краткая диагностика → ещё одна попытка только при бюджете/выгоде. Ограничения
попыток/времени/вывода обязательны. Правки транзакционные; при ошибке откатить
только свои изменения, не чужую работу. Проверка выходного кода без фиксации
хешей тестов недостаточна. Не обещать полную корректность по видимым тестам.

## H. Вывод и аварийное завершение
answer.txt только task_dir/answer.txt. Атомарная запись временного файла в том же
каталоге и os.replace; cleanup временного файла. Не создавать пустые answers,
UNSOLVABLE, SKIP или пояснения вместо требуемого ответа.
Не удалять ответы пользователя при запуске. Для тестов всегда готовить свежую
копию; resume-поведение спроектировать отдельно с input hash и явным флагом.
Logs: stdout/stderr; по явному --metrics-path — writable /tmp или отдельный mount,
не /app и не дополнительный answer в workspace. stdout — статистика, не эталон.

## I. Безопасность выполнения
Внутри final Docker rootfs read-only, tmpfs и mount задач — writable по контракту.
Не требуется GPU/привилегии/docker-in-docker. Subprocess code не получает env
прокси, HOME с секретами, SSH-agent socket и host filesystem. Пути ограничены
задачей, subprocess timeouts/лимиты и ограниченный stdout. Это defense in depth,
а не криптографическая граница между процессами одного пользователя: явно
описать риск общего UID и доступ к /proc, не заявлять невозможность доступа.
Надёжную сетевую изоляцию обеспечивает среда контейнера/политика организаторов.
Тесты неизвестного кода на рабочем VPS запускать только в отдельном ограниченном
контейнере без секретов и лишних mounts; не напрямую от root.

## J. Измерения и упаковка
Структурированные события: prediction, feasibility, skip_reason, reservation,
llm_request, llm_usage, unresolved_usage, verification, answer_saved, task_end.
Не публиковать ключи/сырые персональные данные/внутренние ответы учебного grader.

Внутренние метрики: проверенная награда, фактический расход, reward/1k (для 0
токенов — отдельная zero-LLM статистика), false-skip count и потерянный reward,
recall невыполнимых на размеченной синтетике, abstention rate UNKNOWN, MAE,
ошибка недооценки, coverage интервала, wall time. Это не официальные метрики.

Docker: явный COPY runtime-файлов; не COPY . .; exclude materials/labels/.env/
.git/.venv/.local/регистрационные ключи. Версии, базовый tag и digest фиксировать
после проверки совместимости. Размер <4 GB, репозиторий <100 MB, сборка <1000s,
работа <1h согласно R1; final command всё ещё открытый вопрос.
