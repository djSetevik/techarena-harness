# Техническое задание: TechArena Budget-Aware Harness

## 1. Цель и главный приоритет
Создать автономный Python-проект на базе openJiuwen. На входе — каталог 100 задач
и `BUDGET`, ориентир 100000 приведённых выходных токенов. На выходе — точные
ответы на выбранные задачи, сохранённые по мере решения. Максимизировать сумму
reward у задач, прошедших проверку; неправильный ответ и пропуск дают 0.

Невыполнимая задача — та, которую нельзя точно решить при имеющихся данных.
Не путать это с «сложная», «не успели», «нет подходящего регулярного выражения»,
«модель не ответила» или «тесты сейчас падают». Обнаружение недостаточности
экономит общий бюджет, но не приносит самостоятельных баллов.

## 3. Формат задач из T1
Восемь задач: по две math, search, data_analysis, coding. Каталог каждой содержит
`task.json`; кроме math примеры содержат `workspace/`. Файлы ввода лежат в workspace.
Наблюдаемые поля: task_id, task_type, instruction, reward, check, expected.
Q1 подтверждает удаление expected в финале и сохранение остальных полей.
`check` — подсказка формата проверки, не готовый ответ и не доступ к скрытым тестам.
В примерах встречаются check=exact_int, exact_str, unittest.

Search — локальные markdown-факты и цепочки связей в kb/. Data analysis — CSV.
Math — последовательности арифметических действий с явно заданным округлением.
Coding — исправление Python-модуля без изменения тестов. Это наблюдаемый формат,
не обещание фиксированных имён файлов или неизменных фраз в финале.

## 4. Контракт запуска
Поддерживать `python /app/run_agent.py --tasks-dir /data/tasks`.
Окончательная команда, согласно Q1, должна быть опубликована 9 ноября; в пакете
её нет. Пример из R1 не считать финальной спецификацией.

Официальные env: LLM_BASE_URL, LLM_API_KEY, BUDGET (Q1). R1 также упоминает
OUT/TASKS, но его пример и текст расходятся. Поддержка CLI --tasks-dir обязательна
для текущей версии. Ответ — `task-directory/answer.txt`, не workspace/answer.txt.
Нерешённая/невыполнимая задача остаётся без файла ответа. Для coding сохранять
разрешённые исправленные исходники; детали финальной проверки исходников уточнить.

## 5. Ограничения, которые нельзя забыть
R1: час выполнения, сборка 1000s, образ <4 GB, репозиторий <100 MB без .git,
без GPU, без runtime-загрузок, сеть только через прокси. Зависимости фиксируются.
CPU/агенты/модели/версия SDK имеют противоречия — см. RULES_AND_OPEN_QUESTIONS.
По R1 все восемь примеров выполнимы; ориентировочно в финале 15–25% невыполнимых.
Это доля набора, не порог или квота для классификатора.

## 6. Архитектурное направление (наше предложение, не требование организаторов)
Статический анализ → исходный прогноз стоимости → локальный детектор выполнимости
→ детерминированное решение → планировщик ограниченных LLM-попыток через oJ
→ проверка → немедленная атомарная запись ответа.

Четыре специализированных решателя и один общий бюджет лучше начать с малого:
одна сессия, без веб-интерфейса, Redis, векторной БД, локальных нейросетей,
скачивания моделей и автоматического самообучения в финальном прогоне.
Лёгкий оценщик стоимости можно улучшать по собранным собственным трассам.
Ожидаемое преимущество — не мощность модели, а корректное воздержание от
необоснованных ответов, точный учёт расходов и выбор выгодных задач.

## 7. Окружение владельца
Ubuntu 24.04/Python 3.12, 2 vCPU и 4 GB RAM. Конкурсный Git-проект отдельно
от JiuwenSwarm и heartbeat. Их службы работают и менять их нельзя.
В JiuwenSwarm пользователь подключил qwen3.8-27b-noreason; это подтверждение
технической доступности у пользователя, не устранение противоречия в правилах.
Никаких настоящих ключей, IP или RegID для разработки этого харнесса не нужно.
