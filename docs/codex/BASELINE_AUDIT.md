# Аудит предоставленного starter (не аудит текущего удалённого Git)

Источник: materials/baseline/techarena-harness-starter.zip.
В архиве семь файлов: .gitignore, Dockerfile, README.md, requirements.txt,
run_agent.py, src/solvers.py, src/__init__.py.
Codex должен сначала сравнить этот снимок с реальным рабочим деревом.

## Что уже есть
- CLI --tasks-dir и --max-llm-calls.
- Локальные решатели для нескольких формулировок math/search/data_analysis.
- Coding через Model из openJiuwen; SDK импортируется лениво.
- Выходные файлы через временный файл и replace.
- Docker base python:3.12.12-slim-bookworm; openjiuwen==0.1.19.
- Пользователь сообщил успешную сборку 1.36 GB и native 6/8, claimed reward=16.

## Что исправить
1. `save_answer` записывает и в task directory, и в workspace. Q1 требует рядом
   с task.json; оставить одно место, проверить отсутствие дубликата в свежем запуске.
2. task.json загружается целиком, включая expected. Текущие solver'ы его явно не
   читают, но новый TaskSpec должен допускать только разрешённые поля.
3. Нет чтения BUDGET, actual usage, общего ledger, резерва и прогнозов.
4. used_llm возвращается только после нормального завершения solve_coding;
   исключение после API-вызова не уменьшает счётчик. Это позволяет потерять
   уже оплаченный запрос. Учёт перенести в единственную точку вызова модели.
5. main пропускает все coding-задачи без LLM-бюджета/ключей до запуска tests_pass,
   хотя часть coding-задач может уже проходить тесты без модели.
6. При некоторых исключениях после записи нового кода откат не гарантирован.
   Нужен transactional patch, проверка разрешённых файлов и finally/rollback.
7. tests_pass возвращает лишь bool, теряет диагностику; цикл исправления отсутствует.
8. Math regex может молча не заметить неизвестное действие и вернуть частичный
   расчёт. Проверять покрытие смысловых операций, не каждый служебный текст.
9. Search ищет первый заголовок/поле, не обрабатывает конфликты, альтернативные
   формулировки и доказательство отсутствия факта.
10. CSV привязан к sales.csv/product/month/units и одному виду вопроса; нет
    явной семантики пропусков, дубликатов, неоднозначности и производных величин.
11. Нет feasibility-слоя. `None` смешивает нехватку данных, формат, ошибку и бюджет.
12. Нет LLM-fallback для остальных типов. Не начинать с LLM по каждой задаче:
    сначала безопасный детерминированный путь и классификация UNKNOWN.
13. Жёсткий allowlist/имя модели из старых правил — вынести в профиль и сверить.
14. Тесты выполняются обычным subprocess в контексте хоста. Не называть это
    sandbox и не запускать сгенерированный код под root на рабочем сервере.
15. Нет тестов и метрик для detector, estimator и budget.

## Особенность данных, которую нельзя пропустить
В T1 одинаковые имена сущностей встречаются в разных kb с различными фактами
(например, company_fjord_data.md). Индекс/кэш должны иметь scope конкретной
задачи или хеша набора входных файлов, а не только имя сущности.

## Граница доказанного
6/8 относятся к восьми видимым примерам. Это не 75% на финале, не доказательство
надёжного detector и не подтверждение правильности SDK-вызовов через прокси.
Не объявлять оба coding-примера решёнными до фактического прогона.
