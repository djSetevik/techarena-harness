# TechArena 2026 — инструкции агенту разработки

## Задача
Доработай существующий конкурсный харнесс на openJiuwen, не серверную установку
JiuwenSwarm. Максимизируем проверенную награду на 100 задачах при общем бюджете
BUDGET. Главный приоритет — не тратить LLM-токены на задачи, ответ которых
не определяется доступными данными, и не отбрасывать решаемые задачи.

## Читать перед изменениями
1. `docs/codex/PROJECT_BRIEF.md`.
2. `docs/codex/RULES_AND_OPEN_QUESTIONS.md`, оба исходных текста в
   `docs/codex/materials/original/` и уточнение U1 в
   `docs/codex/materials/clarifications/codex-development-authorization.ru.md`.
3. `docs/codex/BASELINE_AUDIT.md`.
4. `docs/codex/IMPLEMENTATION_SPEC.md`, затем критерии текущего этапа в
   `docs/codex/ACCEPTANCE_TESTS.md`.
5. Назначенный файл из `docs/codex/prompts/`.
Если пакет находится в другом месте, найди его внутри текущего репозитория,
но не сканируй домашний каталог в поисках секретов.

## Границы доступа
Работай только в этом Git-репозитории и его временных тестовых каталогах.
Не трогай `/root/TechArena2026`, `/root/.jiuwenswarm`, `.ssh`, службы systemd,
SSH, firewall, registration/heartbeat и их ключи. Не читай чужие конфиги,
не выполняй `env`, `printenv`, `cat .env`, не выводи токены.
Не меняй систему, не используй sudo, не устанавливай глобальные зависимости.
Не запускать автоматически Docker/привилегированные команды. Не использовать
Docker socket как обход sandbox. Не делать push, force-push, reset --hard,
clean -fd или коммиты без отдельного разрешения. Сначала проверь git status;
не перезаписывай незакоммиченные пользовательские изменения.

## Источники и неясности
Не выдавай проектные решения за правила организаторов. Противоречия сохраняй
в `docs/OPEN_QUESTIONS.md`. По уточнению U1 владелец сообщил об отдельном
разрешении организаторов использовать Codex сугубо для разработки системы.
Для этого проекта вопрос допуска Codex к написанию, отладке и проверке кода
закрыт: не запрашивай повторного разрешения и не блокируй разработку на этом
основании. Старый пункт в OPEN_QUESTIONS отметь решённым со ссылкой на U1.
Это не допуск Codex в финальный runtime: конкурсный харнесс использует
openJiuwen и разрешённые модели через прокси организаторов, не Codex/API Codex.
Остальные ограничения конкурса и границы доступа сохраняются.
При неизвестном API SDK изучи установленную версию и официальные исходники.
Не выдумывай классы/параметры. Не обновляй .venv работающего JiuwenSwarm.

## Инварианты решения
- `task_type`: math, search, data_analysis, coding. Не опирайся на task_id,
  имена примеров, число строк, конкретные ответы или распределение reward.
- `expected` используется только внешним тестовым оценщиком. Не включать его
  в TaskSpec, промпт, признаки, runtime-образ или модель оценки стоимости.
- Контекст одной задачи отделён от других: одинаковое имя сущности в двух
  kb не означает один и тот же набор фактов. Не переносить ответы между ними.
- Feasibility: SOLVABLE / UNSOLVABLE / UNKNOWN. UNSOLVABLE требует проверяемого
  свидетельства недостаточности данных в поддерживаемой семантике. Ошибка
  парсера, пустой grep, падение теста и отсутствие API не являются доказательством.
- Первичная проверка выполнимости работает без вызовов LLM. UNKNOWN не означает
  запрет решения: передай его планировщику для экономически оправданной попытки.
- Ни одной сетевой LLM-операции в обход общего BudgetManager, включая ретраи,
  оценку/классификацию, сжатие контекста и служебные проверки модели.
- Прогноз затрат сохраняется до первой попытки решения; не заменяй его фактом.
- `answer.txt` только рядом с `task.json`, атомарно после полученного ответа.
  Для UNSOLVABLE/UNKNOWN без решения/пропуска по бюджету файл не создавать.
- Не менять task.json, данные или тесты ради прохождения проверки.
  В coding менять только разрешённые исходники; DONE — после проверки.
- Не исполнять код задач и LLM на production-хосте под root. Timeout и AST-фильтр
  не являются полноценной изоляцией. Подпроцессам не передавать секреты.
- Нужна реальная работа openJiuwen; пакет в requirements и пустой import
  сами по себе не являются достаточным инженерным обоснованием интеграции.

## Рабочий режим
Сначала аудит и воспроизводимые offline-тесты. Сетевые обращения к прокси,
установка зависимостей, обновление SDK и нагрузочные прогоны — только после
подтверждения владельца. Сам Codex для работы использует свою модель;
«offline-тесты» здесь означают отсутствие вызовов LLM из конкурсного кода.
Проверяй синтаксис, затем unit/integration-тесты. Не объявляй Docker или
real-API тест успешным, если он не запускался. После этапа запиши изменения,
команды, результаты и блокеры в `docs/PROGRESS.md`. Не оставляй TODO/stub на
обязательном рабочем пути выполненного этапа. Не реализуй все этапы одним махом.
